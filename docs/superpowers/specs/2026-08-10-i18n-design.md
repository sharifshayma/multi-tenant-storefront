# Arabic/English internationalization — design

**Date:** 2026-08-10
**Status:** Approved (pending spec review)
**Branch:** `claude/new-bundle-flow-test-*`

## Problem

The platform (admin dashboard + multi-tenant storefronts) is built Arabic-only:
~85 `.tsx`/`.ts` files contain hardcoded Arabic strings, `dir="rtl" lang="ar"` is baked
into the root layout, and there is no i18n mechanism. Store operators need to switch the
entire UI — their dashboard AND their public storefront — to English, while any
user-entered content (store name, product titles/descriptions, hero/footer copy) stays
exactly as typed.

## Goals

- A single store-level language setting that flips **both** the admin dashboard and the
  storefront between Arabic and English, including layout direction (RTL ↔ LTR).
- All of the app's own chrome (labels, buttons, headings, helper text, validation/error
  messages, customer emails) translates.
- User-entered content is never translated.
- Existing stores (including the book store `shaymas-books`) stay Arabic with zero visible
  change until an operator opts into English.

## Non-goals

- More than two languages.
- Translating user content or auto-detecting a visitor's browser language.
- A third-party i18n library / locale-in-URL routing.
- Separate admin vs storefront languages (one toggle drives both; may be split later).

## Locale model

Add one column to `Store`:

```prisma
uiLocale String @default("ar")   // "ar" | "en"
```

`@default("ar")` means every existing row is Arabic without a backfill. `uiLocale` is the
single source of truth for: (a) which dictionary is used, (b) `dir`/`lang`, (c) the
`Intl` locale for price/number/date formatting (`ar` → `ar`, `en` → `en`). The legacy
`defaultLocale` column is left in place but the app formats via `uiLocale` from now on.

Type alias used throughout: `export type Locale = "ar" | "en";`

## i18n mechanism

New `src/i18n/` module — no external dependency:

- `src/i18n/dictionaries/ar.ts` and `en.ts` — one nested object each, **identical shape**,
  namespaced by area:
  ```ts
  export const ar = {
    common: { save: "حفظ", cancel: "إلغاء", back: "رجوع", loading: "جارٍ التحميل..." },
    admin: {
      nav: { orders: "الطلبات", products: "المنتجات والوسائط", /* … */ },
      orders: { title: "الطلبات", productionList: "قائمة الإنتاج", totalCopies: "{n} نسخة إجمالاً" },
      /* … one sub-object per area … */
    },
    store: { hero: { /* … */ }, cart: { /* … */ }, /* … */ },
    errors: { slugTaken: "هذا الرابط مستخدم بالفعل…", /* … */ },
    email: { /* customer email templates … */ },
  } as const;
  ```
  `en.ts` mirrors the same keys with English values. `ar` is the source of truth for the
  key set; `en.ts` must define every key `ar` defines (enforced by a typed shape — see
  below).

- `src/i18n/index.ts`:
  ```ts
  export type Locale = "ar" | "en";
  export type Dictionary = typeof import("./dictionaries/ar").ar;
  export function getDictionary(locale: Locale): Dictionary; // returns ar or en
  export function t(dict: Dictionary, path: string, vars?: Record<string, string | number>): string;
  export function dirFor(locale: Locale): "rtl" | "ltr";
  ```
  - `en.ts` is typed as `: Dictionary` so a missing/renamed key fails `tsc` — this is the
    completeness guarantee.
  - `t()` walks the dot-path and interpolates `{name}` placeholders from `vars`. On a
    missing path it returns the path string (dev-visible) rather than throwing.

- **Server components** resolve the locale from store context and call
  `const d = getDictionary(store.uiLocale)` then `t(d, "…")` (or a bound helper
  `tt = (p, v) => t(d, p, v)`).
- **Client components** receive the dictionary + locale via a `LocaleProvider`
  (`src/i18n/LocaleProvider.tsx`, a client context) placed in each area layout; they read
  it with a `useT()` hook returning `{ t, locale, dir }`.

## Direction & layout

- Remove `dir="rtl" lang="ar"` from `src/app/layout.tsx` (root). The root `<html>` gets a
  neutral default (`lang="ar" dir="rtl"` stays as the fallback for routes with no store,
  e.g. platform pages); area layouts override per store.
- **Admin dashboard layout** (`src/app/admin/(dashboard)/layout.tsx`) and **storefront
  layout** (`src/app/[storeSlug]/layout.tsx`): resolve the store's `uiLocale`, set
  `dir={dirFor(locale)}` and `lang={locale}` on their top wrapper element, and wrap
  children in `LocaleProvider`.
- Auth pages (`/admin/login`, reset) resolve no store; they use a sensible default
  (Arabic) — acceptable, low priority; can accept a `?lang` later.
- **Physical → logical Tailwind classes** are swapped during conversion so layouts mirror
  automatically: `pr-*`→`pe-*`, `pl-*`→`ps-*`, `mr-*`→`me-*`, `ml-*`→`ms-*`,
  `text-right`→`text-end`, `text-left`→`text-start`, `right-*`→`end-*`, `left-*`→`start-*`,
  `rounded-l-*`→`rounded-s-*`, `rounded-r-*`→`rounded-e-*`. Each converted file is audited
  for these. (Direction-neutral utilities like `text-center`, `gap-*`, `justify-between`
  are left as-is.)

## Errors, emails, tests

- **Server-action error messages:** actions already call `requireStore()`, so they read
  `store.uiLocale`, get the dictionary, and return the **translated** string in
  `{ ok: false, error }`. Call sites are unchanged (still render `result.error`). Pure
  validation helpers in `lib/` that currently return Arabic (e.g. `validateStoreSlug`)
  either take a `locale`/dictionary argument or return a **key** the action translates —
  decided per-helper in the plan; default is the action translates.
- **Customer emails** (`src/lib/resend.ts` / order notifications) render in the store's
  `uiLocale` using the `email.*` namespace.
- **Tests:** assertions that currently hardcode Arabic strings are updated to assert
  through the dictionary (`ar.errors.slugTaken`, etc.) so they are locale-stable. Tests
  that exercise a specific locale set it explicitly.

## Conversion strategy

Two phases:

**Phase A — core (must land first, gates everything else):**
1. `uiLocale` column + migration.
2. `src/i18n/` — `Locale`, `Dictionary` type, `getDictionary`, `t`, `dirFor`, empty-ish
   `ar`/`en` skeletons that grow per batch, unit tests for `t()` (path walk, interpolation,
   missing-key fallback) and en/ar shape parity (tsc-enforced).
3. `LocaleProvider` + `useT()`.
4. Locale resolution + `dir`/`lang` wiring in the admin and storefront layouts.
5. `uiLocale` selector: `updateStoreUiLocale` action + `LanguageCard` in Settings.

**Phase B — string conversion, one batch per area** (each: extract that area's strings into
`ar`/`en` under its namespace, replace with `t()`/`useT()`, swap physical→logical classes,
update that area's tests):
- storefront components (`components/storefront/*`)
- storefront pages (`app/[storeSlug]/**`)
- admin nav + dashboard layout + home (`app/admin/**` shell, `components/admin` nav)
- admin: orders (list + detail + status manager)
- admin: products/books (list, new, detail, forms, media)
- admin: collections (list, new, detail, forms, pickers)
- admin: finance (page, transaction form)
- admin: stock (page, movement form)
- admin: settings (cards already partly built — Branding/Currency/Language/Password/Slug/AutoStock)
- auth (login, password reset, signup)
- shared UI + actions + `lib` messages + emails

Batches are independent once Phase A exists, so they parallelize across subagents. Each
batch is verified by `tsc` + that area's tests + (where visible) a browser check in one
locale.

## Testing

- **Unit:** `t()` behavior (interpolation, fallback); en/ar parity via `tsc`
  (`en: Dictionary`); `updateStoreUiLocale` validation (rejects non-`ar`/`en`).
- **Per batch:** `tsc` clean; existing area tests updated and passing.
- **Manual/visual:** a store toggled to English renders LTR English chrome with Arabic
  user content intact; an Arabic store is unchanged; the admin dashboard flips with the
  same setting.

## Rollout

`uiLocale` defaults to `ar`, so shipping is safe with no data change. The prod migration
adds the column; deploy the code; existing stores stay Arabic until an operator switches in
Settings.
